## Architecture Rules

- Keep `voidb-core` shared and driver-free. It owns traits, shared types, capabilities, profile/config/credential primitives, `ShellCapabilities`, and `SyncWorker`.
- Keep the shell in `crates/voidb-tui/src/app_v4.rs` as a router: tab bar, tab lifecycle, global shortcuts, render/event forwarding, and tab requests only.
- Keep plugin UI, focus, state machines, keybindings, errors, and data loading inside the owning plugin or built-in Connection Manager.
- Treat `ConnectionConfigRegistry` as config metadata. The Connection Manager writes it; plugins read profiles and own live handles through their services.
- Never import database, cloud, mail, or infrastructure driver crates from TUI shell code. TUI code talks to plugin-owned services or capability surfaces.
- For service modules, do not import `ratatui`, `crossterm`, `Frame`, `Rect`, or widget types.

## External-Agent Interaction

- Keep conversation in the external agent. VoidB exposes capabilities and
  plugin-owned context/operation gates, not an embedded agent chat.
- Discover profiles and capabilities through password-free CLI commands before
  requesting access.
- State the concrete task, target, and expected outcome for every authorization
  request. Pass that explanation with `--purpose`; do not merely restate the
  capability name or use a generic phrase such as "run command."
- Prefer a time-bounded authorization request over one-shot approval when the
  user expects follow-up work. Time-bounded grants default to unlimited uses;
  request `--uses` only when the user wants an additional operation-count cap.
- For reusable follow-up access, create `voidb-cli agent request create` with a
  capability or constrained scope. Use the exact request generated by
  `agent exec` only when one normalized invocation is the intended boundary.
- Direct the user to the local CLI review command emitted by the request:
  `voidb-cli agent request review <request-id>`. Prefer this CLI review and
  hidden password prompt over asking the user to open a TUI. Include the
  request purpose and expiry in the handoff so the user can make an informed
  decision.
- Treat an unapproved request as automatically denied when its request TTL
  elapses. Do not ask the user to approve or reuse the timed-out request; create
  a new narrowly scoped request with a current purpose only if the task still
  requires access.
- For multiple known profiles, prepare a narrow JSON grants plan and direct the
  user to `voidb-cli agent authorize-batch --spec <path> --ttl-minutes <n>`.
  The command reviews the whole batch and prompts for the master password once,
  while the broker still creates one isolated grant per immutable profile and
  plugin. Give every grants-plan entry its own concrete `purpose`. Add
  `--uses <n>` only for an explicit finite budget.
- Never ask the user to paste a master password, token, or connection string
  into the conversation. The agent may create or wait on a request, but the
  user completes authorization locally.
- Keep exact or constrained approval for destructive, privilege-escalating,
  local-path, or uncertain operations. A grant never replaces the later
  per-call acknowledgement, dry-run, policy, redaction, and audit gates.
- Prefer capability invocation. Only retained TUIs with material local state
  may share bounded, redacted context; live current-PTY sharing is SSH-only.
- Keep shares generation-bound and expiring. Treat each operation request and
  operation index as a one-shot decision, with replay rejection in the owning
  store.
- Keep the shell and `ShellCapabilities` out of share storage, operation
  dispatch, and live-handle ownership.
- Preserve each plugin's readonly, dry-run, acknowledgement, authorization,
  confirmation, redaction, and audit gates after an operation is requested.

## Key Surfaces

- Core crate: `crates/voidb-core`.
- TUI binary: `crates/voidb-tui`, binary name `voidb`.
- CLI binary: `crates/voidb-cli`, binary name `voidb-cli`.
- External plugin crates: `crates/plugins/voidb-plugin-*`.
- Built-in Connection Manager: `crates/voidb-tui/src/plugins/connection_manager.rs`.
- Capability invocation registry: `crates/voidb-cli/src/builtin/invoke.rs`.
- Plugin CLI registration: `crates/voidb-cli/src/main.rs`.

## Validation

Use the smallest reliable tier from `docs/ci-checks.md`.

- Focused core/shared changes: `cargo test -p voidb-core`.
- TUI shell or Connection Manager changes: `cargo test -p voidb-tui`.
- CLI/profile/invoke/plugin-management changes: `cargo test -p voidb-cli`.
- SQL capability contract changes: plugin tests plus `cargo test -p voidb-cli invoke` and `cargo test -p voidb-core sql_contract`.
- Credential, redaction, capability policy, release, or broad cross-crate changes: add `cargo test --workspace --no-fail-fast` and `cargo clippy --workspace --all-targets --no-deps` when feasible.
- External-agent share or operation-policy changes: run
  `scripts/check-external-agent-interaction.sh`, the affected plugin tests, and
  the full workspace tier for cross-plugin or validation-policy changes.
- Run `git diff --check` before finishing code or documentation edits.

Format touched Rust files with `rustfmt --edition 2024 path/to/file.rs`; avoid whole-repo formatting churn unless the repo already has a clean baseline.
